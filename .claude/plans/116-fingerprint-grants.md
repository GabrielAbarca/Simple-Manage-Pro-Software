## Ticket

**Concern:** The schema fingerprint from #93 reads tables, columns,
constraints, indexes, policies, views, functions and triggers, but not
privileges, enum values or sequences. A live project still granting what the
baseline revokes (`revoke execute on function public.teacher_id() from anon,
public`, `school_schema.sql:668`; `revoke all on public.teachers_directory from
anon, public`, `:637`), or carrying an extra `public.user_role_enum` label,
compares equal to the baseline. The probe also covers grants, enum types and
sequences in `public`, and a compare reports those by kind and name. Keys stop
depending on probe row order.

**User story:** As the owner, I want a project that still grants what the
baseline revokes, or has an extra enum label or a different sequence, to
differ from the baseline fingerprint, so that drift in who can reach what is
caught like any other drift.

**Type:** Enhancement · **Complexity:** Medium
**Portals:** none (delivery tooling) · **Supabase:** yes (`supabase/delivery/`
files only, owner approval; no database, RLS or Auth change, no project touched)

### Patterns to follow

Extension-member filter (`fingerprint.sql:101-105`), reused for types
(`classid = 'pg_type'::regclass`) and sequences (`'pg_class'::regclass`):

```sql
and not exists (
  select 1 from pg_depend d
   where d.classid = 'pg_proc'::regclass
     and d.objid = p.oid
     and d.deptype = 'e')
```

Role name with PUBLIC as `0` (`fingerprint.sql:73-74`):

```sql
case when u.r = 0 then 'public' else pg_get_userbyid(u.r) end
```

## Data contract (additions)

| kind       | on   | name                                                             | definition (before hashing)                                                   |
| ---------- | ---- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `grant`    | null | `<object>.<grantee>.<PRIVILEGE>`                                 | `grantable` or empty                                                          |
| `type`     | null | `public.<enum>`                                                  | `enum (` + labels as `quote_literal`, comma-joined in `enumsortorder` + `)`   |
| `sequence` | null | the owning column `public.<table>.<column>`, else `public.<seq>` | `format_type(seqtypid)`, `start`, `increment`, `min`, `max`, `cycle` when set |

- **Grants:** one row per distinct (object, grantee, privilege) from
  `aclexplode` over `coalesce(relacl, acldefault(…, relowner))` for relations
  in `public` (`r`, `p`, `v`, `m`, `S`, extension members excluded) and
  `coalesce(proacl, acldefault('f', proowner))` for functions (`f`, `p`).
  `<object>` is the same name the table, view or function row uses
  (`public.teacher_id()`, `public.teachers_directory`); a sequence's is
  `public.<seq>`. Grantee `0` is `public`. The owner's own privileges and the
  grantor are left out (Open questions 2, 3).
- **Sequences:** an owned sequence (`pg_depend` `deptype` `a` or `i` on a
  column) is named by its owning column, so a generated sequence name never
  shows, as column defaults already hide it (Open question 1).
- **Keys:** `objectKey` appends `.` + the first 8 hex of SHA-256 of the raw
  identity whenever `keySafe` changed anything other than `", "` → `","`, so
  names that slug alike get distinct keys from their own names. Rows are
  sorted by (kind, name, definition) before keying, so the remaining `.2`
  (two identical constraints or indexes on one table, keyed by definition) no
  longer follows probe order (Open question 4).

## Open questions / assumptions

Each has a default the loop uses if the reviewer approves without overriding it.

1. An owned sequence's generated name (`students_id_seq`) differs by how the
   table was made. — **Default:** name it by its owning column
   (`sequence:public.students.id`); a free sequence keeps its own name.
   Resolved: default stands.
2. The object owner's privileges are implicit, and the owner role can differ
   between CI's install and a live project. — **Default:** grants to the
   owner are left out. Resolved: default stands.
3. The same privilege can come from two grantors (`postgres` and
   `supabase_admin`). — **Default:** the grantor is dropped and duplicates
   merge into one row, `grantable` if any grant was. Resolved: default stands.
4. Two constraints or indexes with the same definition on one table still
   share a key. — **Default:** they keep `.2`, assigned over a sorted order
   instead of probe order; a name hash there would make a rename visible,
   which #93 ruled out. Resolved: default stands.
5. Which names get the hash suffix. — **Default:** only names the slug
   changes (8 hex); lossless names (tables, columns, functions) keep today's
   keys. Policies with spaces change keys; no record holds an exception yet
   (`supabase/delivery/records/` is empty), so nothing breaks. Resolved:
   default stands.

## Notes

- The JS change is small; the risk is the SQL, which nothing local can run.
  Task 5 proves it in CI before the expected files are regenerated, so a bad
  probe fails a focused test rather than a 1,300-object diff.
- Supabase's default privileges grant anon, authenticated and service_role
  everything on new tables and functions, so the school file grows by several
  hundred `grant` objects. That is the point: each one is a privilege a
  project could lose or gain.
- Risk: the CLI's Postgres may set up roles or default privileges differently
  from hosted projects; that surfaces in #102's triage, not here.
- Confidence 7: as in #93, the first CI run of new catalog SQL is where a
  second pass is likeliest.
