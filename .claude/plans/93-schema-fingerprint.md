## Ticket

**Concern:** A read-only catalog probe, `supabase/delivery/fingerprint.sql`,
hashes every object in `public`: tables, columns, constraints and indexes
(compared by definition rather than by name, the root of PRD evidence 2), plus
policies, views, functions and triggers. A compare reports objects added,
removed or changed, by kind and name, after subtracting recorded exceptions.
CI generates the expected fingerprint for each project type from the baseline
(plus the lock for the demo) and fails when the committed
`supabase/delivery/expected/{school,demo}.json` are stale, so the owner's
machine needs neither Docker nor Postgres.

**User story:** As the owner, I want a project's schema reduced to a
fingerprint I can compare with what the baseline says it should be, so that a
renamed-but-identical constraint is not drift and a dropped policy is.

**Type:** New capability · **Complexity:** Medium-High
**Portals:** none (delivery tooling) · **Supabase:** yes (new files under
`supabase/delivery/`, no database, RLS or Auth change, no project touched)

## Data contract

**Probe row** (one cell per row, JSON text):
`{ "kind": string, "on": string | null, "name": string, "definition": string }`

| kind         | on               | name                         | definition (before hashing)                                                             |
| ------------ | ---------------- | ---------------------------- | --------------------------------------------------------------------------------------- |
| `table`      | null             | `public.<table>`             | relkind, `relrowsecurity`, `relforcerowsecurity`                                        |
| `column`     | `public.<table>` | `public.<table>.<column>`    | `format_type`, not null, `pg_get_expr(adbin)` default, identity, generated, collation   |
| `constraint` | `public.<table>` | `public.<table>.<conname>`   | `contype` + `pg_get_constraintdef(oid)`                                                 |
| `index`      | `public.<table>` | `public.<table>.<indexname>` | `pg_get_indexdef(indexrelid)`                                                           |
| `policy`     | `public.<table>` | `public.<table>.<polname>`   | cmd, permissive, sorted role names, `pg_get_expr(polqual)`, `pg_get_expr(polwithcheck)` |
| `view`       | null             | `public.<view>`              | relkind, `reloptions` (keeps `security_invoker`), `pg_get_viewdef(oid, true)`           |
| `function`   | null             | `public.<name>(<args>)`      | `pg_get_functiondef(oid)` (prokind `f`/`p` only: it errors on aggregates)               |
| `trigger`    | `public.<table>` | `public.<table>.<tgname>`    | `pg_get_triggerdef(oid)`, `not tgisinternal`                                            |

Extension-owned objects (`pg_depend.deptype = 'e'`) are left out.

**Normalisation** (in JS, so it is unit-tested): an index definition drops its
own name (`CREATE [UNIQUE ]INDEX <name> ON` → `CREATE [UNIQUE ]INDEX ON`); a
column default's sequence name becomes a placeholder
(`nextval('<seq>'::regclass)` → `nextval(<sequence>)`). Constraint definitions
carry no name already.

**Key:** constraint and index keys are `<kind>:<on>.<first 16 hex of the
definition's SHA-256>`, so a rename is invisible and a new definition is
removed + added. Every other key is `<kind>:<name>` with `", "` → `","` and any
character outside `[A-Za-z0-9_.,()]` → `_`. A key longer than 200 characters is
cut and suffixed with `.` + 16 hex of the full key. A duplicate key (two
identical constraints on one table) gets `.2`, `.3`, …

**Fingerprint:** `{ digest, objects }`, `objects` keyed and sorted by key, each
`{ kind, name, hash }` (`hash` = SHA-256 hex of the normalised definition).
`digest` = SHA-256 hex over `key\thash\n` lines in key order; it is the
64-hex `fingerprint.before/after` #90's record stores.

**Comparison:** `{ equal, added, removed, changed }`, each a sorted list of
`{ key, kind, name }`. `name` comes from the side that has the object (the
actual side for `changed`). Exceptions are `{ key, reason }[]`; a difference
whose key is excepted is dropped before `equal` is computed.

**Serialised file:** `JSON.stringify({ digest, objects }, null, 2) + "\n"`,
objects only (no arrays), so Prettier leaves it unchanged.

## Open questions / assumptions

1. Policy and function names carry spaces and other characters #90's exception
   `object` rejects. — **Default:** keys are slugged into #90's shape (see Key
   above); the human-readable `name` is kept beside each key. `record.mjs` is
   not changed. Resolved: default stands.

   reach what, but the ticket doesn't list them. — **Default:** left out here;
   noted under "Not in this change" as a follow-up for the epic. Resolved: default stands.
3. Indexes that back a primary-key or unique constraint appear twice (as the
   constraint and as its index). — **Default:** keep both. Both compare by
   definition, so a rename stays invisible and nothing is double-hidden. Resolved: default stands.
4. How the owner refreshes the committed files after a schema change. —
   **Default:** CI's `expected-fingerprints` artifact, copied into
   `supabase/delivery/expected/`; documented in the map row. A
   `docs/DELIVERY.md` section is the epic's later doc ticket. Resolved: default stands.

## Notes

- Hashing happens in JS, not SQL, so normalisation is unit-tested and the
  probe stays a plain catalog read. The JSON-per-row cell exists only because
  the psql executor splits rows on newlines.
- `pg_get_viewdef` and `pg_get_functiondef` text can differ between Postgres
  majors. The harness runs 17 like the projects (#87); a mismatch on a live
  project is #102's triage, not a defect here.
- Risk: the CLI image may put objects in `public` that a live project doesn't
  have (or the reverse). Extension members are excluded; anything else shows
  up in #102.
- Risk: task 6 depends on a CI round trip, and tasks 4 and 6 depend on the
  guard prompt being answered. Both are attended steps.
- Confidence 7: the compare is straightforward; the probe's catalog SQL and
  the first CI-generated files are where a second pass is likeliest.
